## 5. Build and runtime facts verified locally [R]

- `npm run build` succeeds (Astro 7.4.13 + adapter 8.2.14), emits `dist/` and `.netlify/v1/functions/ssr/ssr.mjs`; middleware mode is `classic`.
- `npm run check`, `npm run lint`, `npm test`, `npm audit --audit-level=high` (exit 0; 10 moderate transitive advisories, accepted-and-tracked per ADR-001 R15, Sasha decides) pass.
- `astro dev` daemonises only when it detects an AI agent / non-interactive caller (`isRunByAgent()` in `node_modules/astro/dist/cli/dev/index.js`; `ASTRO_DEV_BACKGROUND` disables the detection).
  **`astro dev --ignore-lock` always runs a one-off foreground server** (verified with 7.4.13) and is what Playwright's `webServer` uses.
  This refines ADR-001 D7: it is agent-detection auto-backgrounding, not unconditional.
- `astro dev` starts the DB emulator and writes `.netlify/state.json` (connection string) **after** startup, but does not apply migrations (PoC D4).

## 6. Migrations: on deploy vs explicit

- **Production/previews:** Netlify applies native migrations before publish [A, ADR-001 F5]. We rely on this; **CI and the repo never hold production credentials**.
- **Local, tests, CI:** explicit `npm run db:migrate` (`scripts/migrate.ts`, `applyMigrations` over postgres.js; connection from `NETLIFY_DB_URL` or `.netlify/state.json`).
  Re-runs are no-ops. The script **refuses a non-local host unless `--remote` is passed** so it cannot hit production by accident. `MIGRATIONS_DIR` overrides the folder (used for testing the runner).
- Forward-only, expand/contract (ADR-001 F5). Never edit an applied migration. A bad migration is fixed by a new migration, not by rewriting history.
- Risk: if `NETLIFY_DB_URL` is **not** available at build time on Netlify, deploy-time migration cannot run; the fallback is the user running `NETLIFY_DB_URL=... npm run db:migrate -- --remote` once [A: verify on first deploy].

## 7. First production seed path (evaluation)

| Option | Verdict |
|---|---|
| A. User runs `npm run db:reset-seed` against production once (Marcus's recommendation) | **Chosen for the first seed.** There is no Admin user before any seed, so the in-app reset (B) cannot bootstrap. It runs in about 1 s locally, and is not bound by the 60 s function limit |
| B. Admin "Reset demo data" action (`DEMO_RESET_ENABLED=true`) | **Chosen for later resets only**, after the first seed created the Admin. Changing an env var needs a redeploy to take effect [A], so it costs 15 credits: enable it only for a demo window |
| C. Seed as a migration | Rejected (ADR-001 §5: migrations run on every deploy/branch) |
| D. Seed during build | Rejected: build runs on every deploy, would wipe data, and mixes build and data concerns |

Procedure for A (the user performs it; the connection string is a secret):

```bash
# Obtain the production connection string from the Netlify UI (Database page) [A] and keep it out of files and history.
read -rs NETLIFY_DB_URL && export NETLIFY_DB_URL      # paste, Enter; nothing is echoed or saved
npm run db:migrate -- --remote                        # only if the deploy did not already apply migrations
npm run db:reset-seed -- --remote                     # TRUNCATE + deterministic seed (destructive on that DB)
unset NETLIFY_DB_URL
```

Requirements for Dana's `scripts/reset-seed.ts`: reuse the host guard (refuse non-local unless `--remote`), print the host (not the password) and the row counts, and run in one transaction.
Risks: (1) the hosted DB may not accept connections from outside Netlify [A]; if so, fall back to B with a temporary `DEMO_RESET_ENABLED=true` plus a one-time bootstrap
(Marcus/Diego decide whether a first-run bootstrap admin is acceptable; that would be an ADR-003 matter, not decided here). *[Sasha T-027]* Any bootstrap path needs a new security review before it is built; an unauthenticated or GET bootstrap endpoint is not acceptable. (2) Network round trips: about 12 batches plus begin/commit, so expect a few seconds [A].

## 8. Deploy-preview and credit policy (Free plan: 300 credits/month, hard stop) [A: rates from ADR-001 F8]

Policy [P]:

1. **Production only.** In Netlify: Deploy previews = **None** (no automatic previews for PRs); Branch deploys = **None**. Re-enable previews only with user approval, for a single PR, then switch off again.
2. **No auto-publish surprises:** leave "Auto publishing" on only if the user accepts that every merge to `main` costs a deploy; otherwise **lock publishing** (Deploys > Stop auto publishing) and publish manually after approval. Because every push to `main` triggers a build, we also use:
3. **Skip builds on non-app changes** by starting a commit message with `[skip ci]` / `[skip netlify]` for docs-only commits [A: Netlify honors these markers]. Netlify's `ignore` command is **not** used in v1 (a wrong `ignore` could silently block a needed deploy).
4. **Batch merges**: target at most 1 or 2 production deploys per week, 8 per month.
5. GitHub Actions minutes are separate from Netlify credits and cost nothing on a public repo [A].

Monthly budget [P] (all figures from ADR-001 F8; the user confirms current rates on the Usage page):

| Item | Rate [A] | Allowance | Credits |
|---|---|---|---|
| Production deploys | 15 each | 8 | 120 |
| Database compute | 10 per CU-hour, sleeps after 5 idle minutes | 10 CU-hours (about 20 short demo sessions) | 100 |
| Functions, requests, bandwidth, DB bandwidth | small for a class demo | | 50 |
| Reserve | | | 30 |
| **Total** | | | **300** |

Usage checks: Netlify UI **Team > Usage / Billing** before the first deploy, before every later deploy, and weekly. Stop and tell the user at **>= 200 credits used** (about two thirds); stop all deploys at **>= 270**.
Do not enable auto-recharge, upgrades or add-ons. If credits run out, the site pauses: the fallbacks in ADR-001 §4 need explicit user approval.
Local-first: all development and tests use the emulator and `@netlify/database-dev`, which cost no credits.

## 9. Security headers

`netlify.toml` `[[headers]] for = "/*"` (draft for Sasha):

| Header | Value | Why |
|---|---|---|
| Content-Security-Policy | *[Sasha T-027 correction: `style-src 'self'`, no `'unsafe-inline'`, identical to ADR-003 D-12]* `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'; upgrade-insecure-requests` | Chart.js is bundled from npm, so no CDN. `astro.config.mjs` sets `build.inlineStylesheets: 'never'` and `vite.build.assetsInlineLimit: 0`, so scripts and styles are external files and **no inline script is needed or allowed**. `style-src` keeps `'unsafe-inline'` only so inline `style=""` attributes do not break pages; tightening it is a follow-up for Maya/Felix/Sasha (Chart.js sets styles through the CSSOM, which CSP allows) |
| X-Frame-Options | `DENY` | legacy clickjacking guard alongside `frame-ancestors 'none'` |
| X-Content-Type-Options | `nosniff` | |
| Referrer-Policy | `strict-origin-when-cross-origin` | |
| Permissions-Policy | camera, microphone, geolocation, payment, usb disabled | |
| Strict-Transport-Security | `max-age=31536000` | Netlify serves HTTPS only; no `preload`, no `includeSubDomains` (shared `*.netlify.app` domain) |
| Cross-Origin-Opener-Policy | `same-origin` | |

[A] Netlify `[[headers]]` apply to CDN/static responses; headers on **SSR function responses** may not be applied from `netlify.toml`.
**Requirement for Diego (`src/middleware.ts`):** also set the same CSP, frame, nosniff, referrer and permissions headers on every SSR response
(one shared constant is preferable), and tests assert them. Do not use inline `<script>` or `set:html` in pages (Felix/Kenji): the strict `script-src` will block them.
Chart data must be fetched from `/api/v1/kpis` or read from an `application/json` data block (not executed, so CSP-safe).
The dev server does not use these headers; verify the CSP once against a production build when a way to serve it locally exists, otherwise on the first deploy.

## 10. CI (`.github/workflows/ci.yml`)

Triggers: push to `main`, pull requests. Permissions: `contents: read`. **No deploy step, no secrets.**

| Job | Steps |
|---|---|
| `verify` | checkout, setup-node (`.nvmrc`, npm cache), `npm ci`, `npm run check`, `npm run lint`, `npm test`, `npm audit --audit-level=high`, `npm run build` |
| `e2e` (needs `verify`) | `npm ci`, `npx playwright install --with-deps chromium`, `npm run test:e2e` (Playwright `webServer` = `astro dev --ignore-lock`, foreground); uploads report on failure |
| `secret-scan` | full-history checkout + `gitleaks/gitleaks-action@v2` (free for personal-account repos [A]; if the repo lives in an organization the action needs a free license key stored as a repo secret, which the user would add) |

Actions are pinned to major tags; pinning to commit SHAs is a hardening follow-up (the SHAs could not be looked up offline). The e2e job has not run on GitHub yet (ADR-001 §12.1 item 8): the sequence is verified locally only (`npm run test:e2e`, 1 test passed).
Playwright global setup (migrate + small-fixture seed) is Quinn's/Dana's to add in `tests/e2e/`. Never skip a failing test to get green.

## 11. Rollback

- **App:** Netlify UI > Deploys > pick the last good deploy > **Publish deploy** (instant, no rebuild, so no build credits [A]); this also stops auto publishing, so re-enable it after the fix.
- **Schema/data:** migrations are forward-only. Ship a corrective migration (expand/contract keeps the previous app version compatible with the new schema, so a code rollback is safe). Database backups/branch restore: confirm availability on the Free plan [A] (ADR-001 F5).
- **Demo data:** for a corrupted demo, rerun the seed (§7); data is fictional and reproducible.
- **Credits exhausted/site paused:** do nothing automatic; report to the user (§8).
