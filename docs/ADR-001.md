## 1. Context

**What we must deliver:** `docs/project-scope.md` §3, version 1. That means shipments with a status lifecycle
and pack/verify checks, packaging errors, rework and corrective actions, receipts, an append-only
inventory ledger, cycle counts, lot trace, a dashboard with 6 KPIs and charts C1–C6, reports R1–R8 with
CSV export, and fictional seed data with a reset.

**New requirement from the user:** the app must **deploy on Netlify**, and records must **persist**.

**Security baseline:** `docs/07-software-design.md` §7.2. That means login, server-side role checks on every
write, hashed passwords, CSRF and session safety, parameterized queries, server-side validation, an
append-only audit log, secrets kept in environment variables, and generic error pages.

**Team constraint:** this is a graduate-class prototype built by a small team of AI agents. We want one
repo, one deployable, minimal dependencies and the free tier.

**The original proposal** (`docs/07` §7.1) was Python 3 + Flask, SQLite through SQLAlchemy,
server-rendered templates, Chart.js, pytest, and a local run only. `docs/project-scope.md` §4 deferred
"PostgreSQL, Docker deployment, cloud hosting" to v2. **The new Netlify requirement conflicts with that
deferral**, so this ADR proposes a scope edit (§11). The edit needs product-manager (Priya) and user approval.

### 1.1 Verified platform facts (they drive the decision)

| # | Fact | Tag |
|---|------|-----|
| F1 | Netlify Functions have three language options: **TypeScript, JavaScript and Go**. Go uses a Lambda-compatible API. **Python is not offered.** Netlify community answers also say Python functions are not supported. Python is available in the *build* image only (`PYTHON_VERSION`), not as a function runtime. | [R] |
| F2 | Netlify runs each function in an **ephemeral runtime environment** and scales it automatically. A SQLite file written by a function would not persist and would not be shared between instances. | [R] |
| F3 | Function limits: synchronous **60 s**, scheduled 30 s, background 15 min. Memory 1024 MB by default. Buffered payload 6 MB. Runtime is Node.js; the fallback default is Node 24. | [R] |
| F4 | **Netlify Database** is a managed Postgres built into Netlify (built on Neon). It became generally available on 2026-04-28. Adding the `@netlify/database` package auto-provisions it. Code connects through `getDatabase().sql` or `getConnectionString()`, or through the `NETLIFY_DB_URL` env var with any Postgres driver (`pg`, `postgres`, Drizzle). The beta `@netlify/neon` is deprecated. | [R] |
| F5 | **Migrations** are SQL files in `netlify/database/migrations/NNNN_slug(.sql \| /migration.sql)`. Netlify applies them on every production deploy, just before publish; a failure blocks the publish. Deploy previews get their own **database branch**, copied from production data. Migrations are forward-only, and Netlify recommends expand/contract for breaking changes. | [R] |
| F6 | **Local dev:** `netlify dev`, or the Netlify Vite plugin, starts a real local Postgres-compatible database. Supporting commands are `netlify database migrations apply`, `status`, `connect` and `reset` (local only). `@netlify/database-dev` starts an in-memory Postgres for tests, with `applyMigrations()`. Requires Netlify CLI ≥ 26 and Node ≥ 20.12.2. | [R] |
| F7 | **Astro** has an official Netlify adapter. On-demand (SSR) pages run as Netlify Functions. Since Astro 5.12, `astro dev` emulates Functions, Blobs, **Netlify Database**, headers, redirects and env vars without the CLI. Astro's `security.checkOrigin` defaults to `true` (an Origin-header CSRF check for on-demand pages). | [R] |
| F8 | **Netlify Database billing.** It is available only on credit-based plans; all new accounts since 2025-09-04 are on these. **Free plan: 300 credits per month with a hard limit. When credits run out, all projects are paused** ("Site not available"). DB compute costs 10 credits per CU-hour, and the Free plan has 1 CU maximum, sleeps after 5 min idle, and caps usage at 48 CU-hours per database per month. Other costs: DB bandwidth 20 credits/GB, function compute 10 credits/GB-hour, 10k web requests 2 credits, each **production deploy 15 credits**. Deploy previews are not metered *as deploys*. Storage is currently free (5 GB cap on Free). Free also allows 3 databases, 20 branches, and backups of the last published deploy plus 3 days of scheduled backups. | [R] |
| F9 | Netlify Blobs is key/value object storage. Netlify's guidance is that structured, dynamic data belongs in the database. | [R] (seed note, re-checked via the Functions overview) |
| F10 | The Free plan does not support Git contributors committing through **organization-owned private repos**. The repo must be public, or deployed from the owner's personal account. | [R] |
| F11 | Neon's own free plan (an alternative managed Postgres) gives each project 100 CU-hours per month at 0.25 CU, scales to zero when idle, and allows 0.5 GB of storage. These figures come from search excerpts; the Neon site was not fetched directly. | [A] |

## 2. Options considered

### Option A — Flask + SQLite + Chart.js, as proposed in docs/07 §7.1

- **A1, deployed to Netlify:** not feasible. Python is not a Functions runtime (F1), and a SQLite file
  would be lost or diverge between instances (F2). The only workarounds are a second hosting platform for
  Python, or a WASM/sidecar hack. Both break "one deployable".
- **A2, local-only (the honest "simplest" variant):** run Flask + SQLite on a laptop and skip Netlify.

| | A1 (on Netlify) | A2 (local only) |
|-|-----------------|-----------------|
| Pros | Familiar; matches the research docs | Simplest possible dev story; SQLite needs zero setup; pytest is easy; Jinja auto-escaping; Flask-WTF CSRF |
| Cons | **Cannot run on Netlify Functions**; writes would not persist | **Fails the hard requirement** (no Netlify deploy); no shared demo URL for the class; SQLite→Postgres migration later |
| Risks | Hidden second platform, two deployables, credentials sprawl | User rejects the deliverable; "works on my machine" demos |
| Effort | High (workarounds) | Low |

### Option B — Static front end + Netlify Functions (TypeScript) JSON API + Netlify Database + Chart.js

Plain HTML/CSS/TS pages are served from the CDN, and every screen fetches `/api/v1/*` handlers written
as individual Netlify Functions.

- **Pros:** fewest framework dependencies; uses Netlify primitives directly; the API contract
  (`api-contract` skill) maps 1:1 to functions.
- **Cons:** every page renders on the client. That means hand-built routing, templating, HTML escaping
  (`innerHTML` is an XSS risk), form handling and session gating, so there is more code for agents to get
  right. We would also hand-roll CSRF and shared middleware across about 40 function files.
- **Risks:** inconsistent auth checks across functions, and XSS via careless DOM writes.
- **Effort:** medium–high.

### Option C — Astro (SSR) with the official Netlify adapter + Netlify Database + Chart.js  ← recommended

Astro on-demand pages render HTML on the server, much like Flask/Jinja did in the original proposal.
Astro endpoints under `src/pages/api/v1/` give us the JSON API. The adapter turns both into Netlify
Functions in **one deployable**. Data lives in Netlify Database (Postgres). Charts are Chart.js, bundled
from npm and run in a small client script.

- **Pros:**
  - It keeps the original design intent: server-rendered pages and no SPA.
  - Astro escapes `{expressions}` automatically.
  - Built-in Origin-check CSRF (F7).
  - One middleware gives a single auth/role gate.
  - File-based routing.
  - `astro dev` emulates Netlify Database locally (F6/F7).
  - Native Netlify migrations (F5).
  - It is still only TypeScript + SQL.
- **Cons:** adds one framework (Astro) and its build step. Agents must learn Astro conventions. Prices,
  limits and plan rules are set by Netlify (F8).
- **Risks:** a framework/adapter version drift, and a past `checkOrigin` bypass advisory in Astro, which
  we mitigate by pinning a patched version and adding our own CSRF token (§8). Also the credit budget (§12).
- **Effort:** medium.
- **C-alt (fallback within the same option):** same code, but the connection string points at an
  external **Neon free** Postgres instead of Netlify Database. Migrations would then run from the build
  command instead of Netlify's native system (F5 "manual migrations"). Use this only if Netlify Database
  credits prove insufficient.

### Option D — Static Netlify site + hosted backend-as-a-service (e.g., Supabase: Postgres + Auth + RLS)

The browser talks to the BaaS directly. Access control lives in row-level-security policies.

- **Pros:** generous free DB; auth is provided; little server code.
- **Cons:**
  - Two vendors and two accounts.
  - Role checks and status-transition rules move into RLS policies and SQL functions, which are hard to
    review and test for this team.
  - The browser holds an API key.
  - The verifier ≠ packer rule and the append-only ledger become database-policy work.
- **Risks:** a misconfigured RLS policy is an access-control failure (OWASP A01). There is also a vendor
  MCP/tooling temptation to touch real projects.
- **Effort:** medium, with high review cost.

### Option E — Netlify static site + read-only demo snapshot (JSON or SQLite built at deploy time)

- **Pros:** trivial; free; fast.
- **Cons:** **writes do not persist** (the brief asks for persistent shipment and inventory records), so
  it cannot meet acceptance criteria 1–4 except locally.
- **Effort:** low. It is usable only as an emergency fallback for a "view the dashboard" demo.

### Rejected store: Netlify Blobs as the primary database

Blobs is key/value storage (F9). We need joins, foreign keys, the `SUM(qty_change)` on-hand view,
transactions for "ship = status + ledger + audit", and aggregate KPIs. Blobs would push all of that into
application code. Blobs is not used in v1.

## 3. Evaluation

Scoring: each criterion 1 (poor) – 5 (excellent). Weights from the `architecture-decision-records` skill:
high = 3, medium = 2, so the maximum is 75.
**Gate:** criterion 1 is a must-have from the user, so any option that scores ≤ 2 on it is
**disqualified**, whatever its total.

| Criterion (weight) | A1 Flask+SQLite on Netlify | A2 Flask+SQLite local | B Static+Functions+NetlifyDB | **C Astro SSR+NetlifyDB** | D Static+Supabase | E Static snapshot |
|---|---|---|---|---|---|---|
| 1 Netlify with persistent shared data (3) | 1 | 1 | 5 | **5** | 4 | 2 |
| 2 Simplicity for agent team / timeline (3) | 2 | 5 | 3 | **4** | 3 | 5 |
| 3 Supports v1 scope §3 incl. roles, audit, ledger, reports (3) | 2 | 5 | 4 | **5** | 4 | 1 |
| 4 Security posture per docs/07 §7.2 (2) | 3 | 4 | 3 | **4** | 3 | 3 |
| 5 Local dev + automated tests easy (2) | 4 | 5 | 4 | **4** | 3 | 4 |
| 6 Cost: free tier sufficient (2) | 3 | 5 | 3 | **3** | 4 | 5 |
| **Weighted total (/75)** | **35** | **61** | **56** | **64** | **53** | **48** |
| Gate (criterion 1 ≥ 3) | ✗ disqualified | ✗ disqualified | ✓ | **✓** | ✓ | ✗ disqualified |

Notes on the scores:

- A2 has the second-highest raw total. It is the best *local* stack, but it fails the user's Netlify
  requirement, which is why the gate exists.
- C beats B on simplicity and security because server rendering, auto-escaping, the Origin check and a
  single middleware remove whole classes of hand-written code.
- C scores only 3 on cost because the Free plan's 300-credit hard limit is real (F8; see §12 R1).
- D loses points for two vendors and for moving access control into RLS.

---

## 4. Decision

**[P] Adopt Option C: a TypeScript Astro (SSR) app on Netlify, using the official `@astrojs/netlify`
adapter, Netlify Database (Postgres) for all persistent data, and Chart.js for charts.** The repo is a
single Netlify site with one build.

- The Flask + SQLite + SQLAlchemy + pytest stack in `docs/07` §7.1 is **superseded**. The *design intent*
  stays: a small monolith, server-rendered pages, one relational DB, one KPI module and deterministic seed.
- **Postgres everywhere.** Local dev, tests, previews and production all use Postgres (local emulator,
  `@netlify/database-dev`, Netlify branches). There is no SQLite anywhere, so there is no second SQL dialect.
- **Fallbacks:**
  - If Netlify Database credits are insufficient, switch to C-alt (an external Neon free Postgres via an
    env var).
  - If Netlify becomes unavailable for the class demo, keep the static snapshot (Option E) for read-only
    viewing.
  - Either fallback needs user approval.

## 5. Proposed v1 stack (concrete)

| Concern | Choice | Notes |
|---|---|---|
| Language / runtime | **TypeScript** (strict), **Node.js 24 LTS** pinned in `.nvmrc` and the Netlify `NODE_VERSION` | Node 24 is also Netlify's function fallback runtime (F3). Node ≥ 22.18 runs `.ts` scripts natively (type stripping), so we need no `tsx`/`ts-node` [A: re-check with the pinned version]. |
| Framework | **Astro 5.x** (exact pinned version ≥ the release that fixes the `checkOrigin` advisory) with `output: 'server'` and **`@astrojs/netlify`** | Use the adapter's default middleware placement, which runs in the function. **Do not** set `middlewareMode: 'edge'`, so DB-backed session checks run in Node [A: confirm the default in the spike]. |
| Hosting layout | One Netlify site. Static assets go to the CDN (`dist/`). SSR pages + `/api/v1/*` endpoints run as Netlify Functions generated by the adapter. `netlify.toml` holds the build command, headers and context env | One deployable; deploy previews per PR; production from `main`. |
| Database | **Netlify Database** (managed Postgres), production DB + automatic preview branches | Provisioned by installing `@netlify/database` (F4). |
| DB driver / query layer | **`postgres` (postgres.js)**, connection string from `getConnectionString()` in `@netlify/database` and wrapped in one `src/lib/db.ts` | Tagged-template queries are parameterized by design. `sql.begin()` gives transactions for multi-table actions (ship = status + ledger + history + audit). **`sql.unsafe` is banned** (lint/grep check). We use no ORM, to keep dependencies minimal and the SQL readable for KPI review. If the spike shows a connection problem, `pg` is the fallback (Netlify documents both). |
| Migrations | **Native Netlify Database migrations**: hand-written SQL in `netlify/database/migrations/NNNN_slug/migration.sql`, sequential numbering, created with `netlify database migrations new --scheme sequential` | Forward-only with expand/contract (F5). Locally: `netlify database migrations apply`. Integration tests apply the same folder through `@netlify/database-dev`. |
| DB-level integrity | FKs, CHECK constraints, unique business keys. `BEFORE UPDATE OR DELETE` triggers that `RAISE EXCEPTION` on `inventory_transaction`, `status_history` and `audit_log` (append-only even if app code errs). Timestamps are `timestamptz` (UTC). On-hand is a view | This works regardless of the DB role Netlify hands us [A: least-privilege roles may not be available]. |
| Seed & reset | One deterministic TypeScript generator, `src/lib/seed/` (in-house mulberry32 PRNG, fixed seed, no faker dependency), with two entry points: (1) **`npm run db:reset-seed`** runs `node scripts/reset-seed.ts` against whatever `NETLIFY_DB_URL` points to (locally the emulator); (2) an **Admin-only "Reset demo data"** action, `POST /api/v1/admin/demo-reset`, enabled only when env `DEMO_RESET_ENABLED=true`, for the deployed site | Reset = `TRUNCATE … RESTART IDENTITY CASCADE` on business tables (append-only triggers allow TRUNCATE), then batched multi-row inserts inside one transaction. It must finish well under the 60 s sync limit (F3) [A: about 3k rows; measure in the spike]. The seed is **not** a migration, because migrations run on every preview branch and production deploy. |

| Auth & sessions | Our own small module (ADR-003 finalizes it; see §8): `users` + `roles` tables; passwords hashed with **`node:crypto` scrypt** (zero dependencies, accepted by the security checklist); **DB-backed sessions**; middleware gate; role checks in each write handler | No Netlify Identity or third-party auth in v1: it adds external config, and we still need server-side role checks. |
| KPI module | `src/lib/kpi/`: pure functions + named SQL aggregate queries, the single source for tiles, charts and reports | Required by `docs/07` §7.1 and the `kpi-definitions` skill. |
| Testing | **Vitest** for unit tests (KPI formulas against hand-calculated fixtures, validation, auth helpers) and integration tests (repos + transactions against a real in-memory Postgres via **`@netlify/database-dev`**, with migrations applied). **Playwright** (Chromium) for end-to-end tests of the acceptance flows: create → pack → verify fail → error → rework → ship; 403 per role; receipt→ship on-hand; cycle-count adjust; lot trace | Playwright's `webServer` starts `astro dev` (which emulates Netlify DB), then runs `db:reset-seed` with the **small test fixture** profile [A: the emulator must run headless in CI without `netlify login`; the fallback is `@netlify/database-dev` + `NETLIFY_DB_URL` override]. |
| Static checks | `astro check` (TypeScript), ESLint (with a rule or grep banning `set:html` with user data and `sql.unsafe`), `npm audit --audit-level=high` | Keep the lint config minimal. |
| Local dev story | `nvm use && npm ci && npm run dev` (= `astro dev`, which emulates Netlify incl. DB) → `netlify database migrations apply` → `npm run db:reset-seed` → open `http://localhost:4321`. `netlify dev` is an equivalent alternative. Inspect with `netlify database connect` | No Docker, no local Postgres install (F6). The Netlify CLI is a dev dependency so versions are pinned. |
| CI | **GitHub Actions** on PRs and `main`: Node from `.nvmrc` → `npm ci` → `astro check` + lint → Vitest (unit + integration) → Playwright (Chromium) → `npm audit` → secret scan (e.g., gitleaks; ADR-002 picks the tool). **Deploys are done by Netlify's Git integration**, not CI: a deploy preview per PR, production on merge to `main` (after Security Reviewer sign-off and user approval) | ADR-002 (with devops-engineer) details branch protection, Netlify build settings, and whether every PR gets a preview (see the credit budget, R1). |

## 8. Security notes (maps to docs/07 §7.2 and the security-review-checklist skill)

| # | Control | Implementation in Option C |
|---|---|---|
| 1 | Every route requires login; role checked server-side on every write (A01) | Astro middleware: deny by default (allow-list: `/login`, static assets). `requireRole(locals.user, 'Shipping', …)` at the top of every write handler. 403 + audit entry on violation. Verifier ≠ packer checked in SQL within the verify transaction. Adjustments are Supervisor-only. |
| 2 | Parameterized queries only (A05) | postgres.js tagged templates; `sql.unsafe` banned by a lint/grep check in CI; dynamic sort columns come from allow-lists only. |
| 3 | Output escaping (A05) | Astro escapes expressions by default. `set:html` is banned for user-controlled data. JSON embedded for charts is serialized safely (no `</script>` break-out). |
| 4 | CSRF (A01/A06) | (a) Astro `security.checkOrigin: true` (default; F7). (b) Our own per-session **synchronizer token** in every form and in the `X-CSRF-Token` header for fetch POSTs. This is defence in depth, because Astro had a published `checkOrigin` bypass advisory; we pin a patched version. (c) Cookie `SameSite=Lax`. |
| 5 | Password hashing; no default passwords in production (A04/A07) | `node:crypto.scrypt` with a per-user random salt, constant-time compare (`timingSafeEqual`), and parameters per OWASP guidance (ADR-003 fixes N/r/p). Demo users exist only in seed data and are labelled demo-only. Login rate limit: failed-attempt counter per username + IP in the DB (in-memory counters do not work in ephemeral functions). |
| 6 | Secrets via environment variables; no debug outside dev (A02) | `NETLIFY_DB_URL` is injected by Netlify (F4). `DEMO_RESET_ENABLED` and any future secrets are set in Netlify env vars, never committed. `.env` is git-ignored. Session tokens are random, so no signing secret is needed. Astro dev-only error overlays never ship in builds. |
| 7 | Dependency hygiene (A03) | Exact versions + `package-lock.json`; `npm audit --audit-level=high` in CI; no CDN scripts (Chart.js bundled). We keep runtime dependencies to roughly **astro, @astrojs/netlify, @netlify/database, postgres, chart.js** (zod via Astro). |
| 8 | Server-side validation (A06) | Shared Zod schemas; status transitions only through `POST …/actions/{action}` with per-transition required fields. |
| 9 | Append-only audit log | `audit_log` (user, ts, action, entity, id, old→new JSON) written in the same transaction as the change. DB triggers block UPDATE/DELETE on audit, history and ledger tables. |
| 10 | Generic errors; no stack traces (A02) | Custom 403/404/500 pages; API errors follow the `api-contract` error shape; details go to function logs only, with no secrets or passwords logged. |
| — | Sessions | `sessions` table stores **SHA-256 of a 32-byte random token**. The cookie is `__Host-sid` (HttpOnly, Secure, SameSite=Lax, Path=/). Idle timeout 30 min and absolute 8 h [P; ADR-003 confirms]. Logout deletes the row. The session ID rotates on login. |
| — | Headers | CSP (`default-src 'self'`, no inline script except hashed or Astro CSP), `frame-ancestors 'none'`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Content-Type-Options: nosniff`. Set in `netlify.toml` for static assets and in middleware for SSR responses. |
| — | Demo reset endpoint | Admin role + CSRF token + `DEMO_RESET_ENABLED=true`; audit-logged; disabled by default. |
| — | Data policy | Fictional data only; no outbound integrations; preview branches contain only fictional copies of production. |

Explicitly out of scope (unchanged from docs/07 §7.2): SSO, MFA, encryption at rest beyond the
provider's defaults, a formal pen test, and any compliance claims.

## 9. Consequences

**Positive**

- Real persistence on Netlify, with migrations tied to deploys, and isolated preview databases for safe
  agent experimentation.
- Postgres in every environment, so there is no dialect drift.
- Server rendering keeps the UI simple and secure by default.
- One language (TypeScript) across UI, API, seed and tests.

**Negative / costs**

- The team moves from Python to TypeScript, so the research-doc stack in docs/07 §7.1 is superseded.
- We depend on Netlify's credit-based Free plan (300 credits, hard limit, projects pause when exhausted).
- Migrations are forward-only. The schema skill's "reversible migrations" rule must become
  "forward-only, expand/contract, local reset".

Preview DB branches likely also consume compute [A]. | **Medium–High** | High (demo offline) | Develop and test locally (emulator, free).
