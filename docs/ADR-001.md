## 1. Context

**What we must deliver:** `docs/project-scope.md` §3, version 1. That means shipments with a status lifecycle
and pack/verify checks, packaging errors, rework and corrective actions, receipts, an append-only
inventory ledger, cycle counts, lot trace, a dashboard with 6 KPIs and charts C1–C6, reports R1–R8 with
CSV export, and fictional seed data with a reset.

**New requirement from the user:** the app must **deploy on Netlify**, and records must **persist**.

**Security baseline:** `docs/07-software-design.md` §7.2. That means login, server-side role checks on every
write, hashed passwords, CSRF and session safety, parameterized queries, server-side validation, an
append-only audit log, secrets kept in environment variables, and generic error pages.

**Team constraint:** this is a graduate-class prototype built by a small team of AI agents. We want one
repo, one deployable, minimal dependencies and the free tier.

**The original proposal** (`docs/07` §7.1) was Python 3 + Flask, SQLite through SQLAlchemy,
server-rendered templates, Chart.js, pytest, and a local run only. `docs/project-scope.md` §4 deferred
"PostgreSQL, Docker deployment, cloud hosting" to v2. **The new Netlify requirement conflicts with that
deferral**, so this ADR proposes a scope edit (§11). The edit needs product-manager (Priya) and user approval.

## 2. Options considered

### Option A — Flask + SQLite + Chart.js, as proposed in docs/07 §7.1

- **A1, deployed to Netlify:** not feasible. Python is not a Functions runtime (F1), and a SQLite file
  would be lost or diverge between instances (F2). The only workarounds are a second hosting platform for
  Python, or a WASM/sidecar hack. Both break "one deployable".
- **A2, local-only (the honest "simplest" variant):** run Flask + SQLite on a laptop and skip Netlify.

| | A1 (on Netlify) | A2 (local only) |
|-|-----------------|-----------------|
| Pros | Familiar; matches the research docs | Simplest possible dev story; SQLite needs zero setup; pytest is easy; Jinja auto-escaping; Flask-WTF CSRF |
| Cons | **Cannot run on Netlify Functions**; writes would not persist | **Fails the hard requirement** (no Netlify deploy); no shared demo URL for the class; SQLite→Postgres migration later |
| Risks | Hidden second platform, two deployables, credentials sprawl | User rejects the deliverable; "works on my machine" demos |
| Effort | High (workarounds) | Low |

### Option B — Static front end + Netlify Functions (TypeScript) JSON API + Netlify Database + Chart.js

Plain HTML/CSS/TS pages are served from the CDN, and every screen fetches `/api/v1/*` handlers written
as individual Netlify Functions.

- **Pros:** fewest framework dependencies; uses Netlify primitives directly; the API contract
  (`api-contract` skill) maps 1:1 to functions.
- **Cons:** every page renders on the client. That means hand-built routing, templating, HTML escaping
  (`innerHTML` is an XSS risk), form handling and session gating, so there is more code for agents to get
  right. We would also hand-roll CSRF and shared middleware across about 40 function files.
- **Risks:** inconsistent auth checks across functions, and XSS via careless DOM writes.
- **Effort:** medium–high.

### Option C — Astro (SSR) with the official Netlify adapter + Netlify Database + Chart.js  ← recommended

Astro on-demand pages render HTML on the server, much like Flask/Jinja did in the original proposal.
Astro endpoints under `src/pages/api/v1/` give us the JSON API. The adapter turns both into Netlify
Functions in **one deployable**. Data lives in Netlify Database (Postgres). Charts are Chart.js, bundled
from npm and run in a small client script.

- **Pros:**
  - It keeps the original design intent: server-rendered pages and no SPA.
  - Astro escapes `{expressions}` automatically.
  - Built-in Origin-check CSRF (F7).
  - One middleware gives a single auth/role gate.
  - File-based routing.
  - `astro dev` emulates Netlify Database locally (F6/F7).
  - Native Netlify migrations (F5).
  - It is still only TypeScript + SQL.
- **Cons:** adds one framework (Astro) and its build step. Agents must learn Astro conventions. Prices,
  limits and plan rules are set by Netlify (F8).
- **Risks:** a framework/adapter version drift, and a past `checkOrigin` bypass advisory in Astro, which
  we mitigate by pinning a patched version and adding our own CSRF token (§8). The PoC also showed that
  `checkOrigin` does not cover JSON POSTs (§15, R11), so the token and content-type enforcement are
  mandatory. Also the credit budget (§12).
- **Effort:** medium.
- **C-alt (fallback within the same option):** same code, but the connection string points at an
  external **Neon free** Postgres instead of Netlify Database. Migrations would then run from the build
  command instead of Netlify's native system (F5 "manual migrations"). Use this only if Netlify Database
  credits prove insufficient, and **only with explicit user approval** (new external account; §0).

### Option D — Static Netlify site + hosted backend-as-a-service (e.g., Supabase: Postgres + Auth + RLS)

The browser talks to the BaaS directly. Access control lives in row-level-security policies.

- **Pros:** generous free DB; auth is provided; little server code.
- **Cons:**
  - Two vendors and two accounts.
  - Role checks and status-transition rules move into RLS policies and SQL functions, which are hard to
    review and test for this team.
  - The browser holds an API key.
  - The verifier ≠ packer rule and the append-only ledger become database-policy work.
- **Risks:** a misconfigured RLS policy is an access-control failure (OWASP A01). There is also a vendor
  MCP/tooling temptation to touch real projects.
- **Effort:** medium, with high review cost.

### Option E — Netlify static site + read-only demo snapshot (JSON or SQLite built at deploy time)

- **Pros:** trivial; free; fast.
- **Cons:** **writes do not persist** (the brief asks for persistent shipment and inventory records), so
  it cannot meet acceptance criteria 1–4 except locally.
- **Effort:** low. It is usable only as an emergency fallback for a "view the dashboard" demo.

### Rejected store: Netlify Blobs as the primary database

Blobs is key/value storage (F9). We need joins, foreign keys, the `SUM(qty_change)` on-hand view,
transactions for "ship = status + ledger + audit", and aggregate KPIs. Blobs would push all of that into
application code. Blobs is not used in v1.

## 3. Evaluation

Scoring: each criterion 1 (poor) – 5 (excellent). Weights from the `architecture-decision-records` skill:
high = 3, medium = 2, so the maximum is 75.
**Gate:** criterion 1 is a must-have from the user, so any option that scores ≤ 2 on it is
**disqualified**, whatever its total.

| Criterion (weight) | A1 Flask+SQLite on Netlify | A2 Flask+SQLite local | B Static+Functions+NetlifyDB | **C Astro SSR+NetlifyDB** | D Static+Supabase | E Static snapshot |
|---|---|---|---|---|---|---|
| 1 Netlify with persistent shared data (3) | 1 | 1 | 5 | **5** | 4 | 2 |
| 2 Simplicity for agent team / timeline (3) | 2 | 5 | 3 | **4** | 3 | 5 |
| 3 Supports v1 scope §3 incl. roles, audit, ledger, reports (3) | 2 | 5 | 4 | **5** | 4 | 1 |
| 4 Security posture per docs/07 §7.2 (2) | 3 | 4 | 3 | **4** | 3 | 3 |
| 5 Local dev + automated tests easy (2) | 4 | 5 | 4 | **4** | 3 | 4 |
| 6 Cost: free tier sufficient (2) | 3 | 5 | 3 | **3** | 4 | 5 |
| **Weighted total (/75)** | **35** | **61** | **56** | **64** | **53** | **48** |
| Gate (criterion 1 ≥ 3) | ✗ disqualified | ✗ disqualified | ✓ | **✓** | ✓ | ✗ disqualified |

Notes on the scores:

- A2 has the second-highest raw total. It is the best *local* stack, but it fails the user's Netlify
  requirement, which is why the gate exists.
- C beats B on simplicity and security because server rendering, auto-escaping, the Origin check and a
  single middleware remove whole classes of hand-written code.
- C scores only 3 on cost because the Free plan's 300-credit hard limit is real (F8; see §12 R1).
- D loses points for two vendors and for moving access control into RLS.

## 4. Decision

Accepted by the user 2026-11-25, conditional on T-007 (see §0): **adopt Option C, a TypeScript Astro (SSR)
app on Netlify, using the official `@astrojs/netlify` adapter, Netlify Database (Postgres) for all
persistent data, and Chart.js for charts.** The repo is a
single Netlify site with one build.

- The Flask + SQLite + SQLAlchemy + pytest stack in `docs/07` §7.1 is **superseded**. The *design intent*
  stays: a small monolith, server-rendered pages, one relational DB, one KPI module and deterministic seed.
- **Postgres everywhere.** Local dev, tests, previews and production all use Postgres (local emulator,
  `@netlify/database-dev`, Netlify branches). There is no SQLite anywhere, so there is no second SQL dialect.
- **Fallbacks (none is pre-approved; each needs explicit user approval, §0):**
  - If Netlify Database credits are insufficient, first reduce usage (local-first, fewer production
    deploys, previews off). Only **with explicit user approval**: switch to C-alt (an external Neon free
    Postgres via an env var; a second vendor account).
  - If Netlify becomes unavailable for the class demo, keep the static snapshot (Option E) for read-only
    viewing, or demo locally.
  - A paid Netlify plan or credit purchase is **not** a planned fallback; it may be considered **only
    with explicit user approval**.

## 8. Security notes (maps to docs/07 §7.2 and the security-review-checklist skill)

| # | Control | Implementation in Option C |
|---|---|---|
| 1 | Every route requires login; role checked server-side on every write (A01) | Astro middleware: deny by default (allow-list: `/login`, static assets). `requireRole(locals.user, 'Shipping', …)` at the top of every write handler. 403 + audit entry on violation. Verifier ≠ packer checked in SQL within the verify transaction. Adjustments are Supervisor-only. |
| 2 | Parameterized queries only (A05) | postgres.js tagged templates; `sql.unsafe` banned by a lint/grep check in CI; dynamic sort columns come from allow-lists only. |
| 3 | Output escaping (A05) | Astro escapes expressions by default. `set:html` is banned for user-controlled data. JSON embedded for charts is serialized safely (no `</script>` break-out). |
| 4 | CSRF (A01/A06) — *corrected by T-011 (R11)* | **All three layers below are REQUIRED on every state-changing request** (POST/PUT/PATCH/DELETE, form or JSON). None of them is optional defence in depth. **Why:** the PoC showed that `checkOrigin` blocks cross-origin POSTs only for form-style content types (`application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain` → 403). A POST with a forged `Origin: http://evil.example` and `Content-Type: application/json` **succeeded and changed state** (200). Browsers would normally send a CORS preflight for that request, but the endpoint itself enforced nothing (`docs/poc/poc-report.md` §3.7). (a) **Synchronizer CSRF token (required).** A per-session random token, stored server-side with the session. It goes in a hidden field in every form and in the `X-CSRF-Token` header for every fetch/JSON write. It is verified in middleware with a constant-time compare *before* the handler runs; missing or wrong → 403 + audit entry. (b) **Server-side content-type enforcement (required).** Middleware allow-lists the `Content-Type` per endpoint: `/api/v1/*` writes accept only `application/json`; SSR form handlers accept only `application/x-www-form-urlencoded` (or `multipart/form-data` where a form needs it). Anything else (including a missing type or `text/plain`) → **415** with the `api-contract` error shape, before any parsing or DB work. (c) Astro `security.checkOrigin: true` stays on (covers form posts), plus cookie `SameSite=Lax`. **Tests (required):** the role-matrix e2e/integration suite includes, for every write route, forged-Origin JSON without a token → 403; a wrong content type → 415; a valid token + correct type → success. ADR-003 finalizes the token design. |
| 5 | Password hashing; no default passwords in production (A04/A07) | `node:crypto.scrypt` with a per-user random salt, constant-time compare (`timingSafeEqual`), and parameters per OWASP guidance (ADR-003 fixes N/r/p). Demo users exist only in seed data and are labelled demo-only. Login rate limit: failed-attempt counter per username + IP in the DB (in-memory counters do not work in ephemeral functions). |
| 6 | Secrets via environment variables; no debug outside dev (A02) | `NETLIFY_DB_URL` is injected by Netlify (F4). `DEMO_RESET_ENABLED` and any future secrets are set in Netlify env vars, never committed. `.env` is git-ignored. Session tokens are random, so no signing secret is needed. Astro dev-only error overlays never ship in builds. |
| 7 | Dependency hygiene (A03) — *updated by T-011* | Exact versions + `package-lock.json`; `npm audit --audit-level=high` in CI (gate = high/critical); no CDN scripts (Chart.js bundled). Direct runtime dependencies stay at **astro, @astrojs/netlify, @netlify/database, postgres, chart.js** (zod via Astro). **Known transitive runtime deps** (PoC D3): `@netlify/database` pulls `pg`, `ws`, `waddler`, `@neondatabase/serverless`; the adapter pulls `@netlify/vite-plugin` / `@netlify/dev`; `@netlify/database-dev` (dev only) pulls `@electric-sql/pglite` + `pg-gateway` and is semi-internal (its README calls it an internal building block of `@netlify/dev`), so it is exact-pinned. **10 moderate advisories** at the PoC pins (`glob`/`minimatch` DoS via `@astrojs/netlify > @netlify/vite-plugin > @netlify/dev > … > zip-it-and-ship-it / archiver`; build/dev tooling, not the request path). Decision [P, pending Sasha's sign-off]: **accept and track**. Record them in the security review, re-check on every dependency bump, and remove them when upstream fixes ship. **Never run `npm audit fix --force`**: it would downgrade `@astrojs/netlify` to 6.5.13. Any new high/critical advisory fails CI. |
| 8 | Server-side validation (A06) | Shared Zod schemas; status transitions only through `POST …/actions/{action}` with per-transition required fields. |
| 9 | Append-only audit log | `audit_log` (user, ts, action, entity, id, old→new JSON) written in the same transaction as the change. DB triggers block UPDATE/DELETE on audit, history and ledger tables. |
| 10 | Generic errors; no stack traces (A02) | Custom 403/404/500 pages; API errors follow the `api-contract` error shape; details go to function logs only, with no secrets or passwords logged. |
| — | Sessions | `sessions` table stores **SHA-256 of a 32-byte random token**. The cookie is `__Host-sid` (HttpOnly, Secure, SameSite=Lax, Path=/). Idle timeout 30 min and absolute 8 h [P; ADR-003 confirms]. Logout deletes the row. The session ID rotates on login. |
| — | Headers | CSP (`default-src 'self'`, no inline script except hashed or Astro CSP), `frame-ancestors 'none'`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Content-Type-Options: nosniff`. Set in `netlify.toml` for static assets and in middleware for SSR responses. |
| — | Demo reset endpoint | Admin role + CSRF token + JSON content type + `DEMO_RESET_ENABLED=true`; audit-logged; disabled by default. |
| — | No Astro sessions / no Blobs | The adapter auto-wires Astro sessions to Netlify Blobs (PoC D8). We do not call `Astro.session` (grep check in CI), so no session data goes to Blobs and Blobs uses no credits. Our sessions live only in the `sessions` table. |
| — | Data policy | Fictional data only; no outbound integrations; preview branches contain only fictional copies of production. |

Explicitly out of scope (unchanged from docs/07 §7.2): SSO, MFA, encryption at rest beyond the
provider's defaults, a formal pen test, and any compliance claims.

## 9. Consequences

**Positive**

- Real persistence on Netlify, with migrations tied to deploys, and isolated preview databases for safe
  agent experimentation.
- Postgres in every environment, so there is no dialect drift.
